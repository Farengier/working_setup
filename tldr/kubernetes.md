# Kubernetes
Система автоматизации управления контейнерами:
* Разворачивание
* Самовосстановление
* Обновление
* Масштабирование
* Балансировка

Кубернетес состоит из: 
- **[Control Plane]**: управляющий слой, координирующий кластер
- **[Data Plane]**: набор рабочих узлов на которых выполняются контейнера

## Control plane
Управляющий слой, координирующий кластер

- **kube-apiserver**
  Центральный компонент, дающий доступ к API. Может масштабироваться горизонтально
- **etcd хранилище**
  KV хранилище, хранящее состояние кластера k8s
  Прямого доступа нет, только через API. Важно делать резервные копии.
- **kube-scheduler**
  Менеджер подов, отвечает за назначение подов на ноды.
- **kube-controller-manager**
  Компонент, запускающий контроллеры
- **cloud-controller-manager**
  Взаимодействие с облачным провайдером - заказать ноды, сконфигурировать их.

## Data plane
Рабочий узел в слое данных это сервер на котором запускаются контейнеры. Контейнеры группируются в поды.

Компоненты узла:
- **kubelet**
  Агент, отвечающий за управление контейнерами на данном узле.
  Получает спецификации подов, запускает контейнеры, проверяет состояния, отдает статусы
- **kube-proxy**
  Сетевой прокси, виртуальная сеть сервисов
  Настраивает сетевые правила
  Обеспечивает правильное назначение трафика
  Реализует работу Service и clusterIP
- **Контейнерный рантайм**
  Компонент, отвечающий за запуск контейнеров.
  Поддерживаются различные рантаймы, совместимые с CRI (Container Runtime Intefrace):
    * containerd
    * CRI-O
  - Загружает образ
  - Настраивает изоляцию
  - монтирует FS
  - Запускает процесс контейнера

## Работа
Deployment -> ReplicaSet -> Pod
- Deployment - описание целевой структуры
- ReplicaSet - набор
- Pod 

kubectl apply
* Валидация yaml 
* Отправка манифеста в API
  - Аутентификация
  - Авторизация
  - Адмишн - изменение/проверка объектов
  - Персист - запись в etcd
* Контроллер deployment получает событие, создает дочерний объект ReplicaSet, содержащий шаблон пода и число реплик
* Контроллер replicaSet получает событие, создает нужное количество подов, не привязанных к узлам (nodename пуст)
* Шедулер назначает поды на узлы, следуя политикам, проставляет nodename
* Кублеты соответствующих нод получают задачу запуска подов
* Рантайм запускает контейнер

## Сеть
У каждого пода свой IP, можно общаться между собой напрямую.
У сервисов отдельный диапазон IP-адресов

У сервиса постоянное DNS имя и еще 1 IP - вход в балансировщик
Тип сервиса:
 - ClusterID 
 - LoadBalancer
 - NodePort
 - Ingress
